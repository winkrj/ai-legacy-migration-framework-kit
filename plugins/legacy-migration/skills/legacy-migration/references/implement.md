# 구현 절차

## 0. 승인 확인 — 통과 못 하면 [멈춤 보고]로 종료

- Approved `docs/conventions/binding-rules.md`가 없으면 구현 일관성을 보장할 수 없으므로 모드와 무관하게 [멈춤 보고]한다.
- PASS `reports/baseline-verify-*.txt` 또는 기존 실패 범위가 문서화되고 사람이 승인한 baseline 예외가 없으면 회귀를 분리할 수 없으므로 [멈춤 보고]한다.
- Light: `docs/migration/<기능명>/02_Spec.md`의 구현 승인 체크박스가 `- [x]`인지 확인한다.
- Full: `03_Plan.md`의 `Implementation Permission: Granted*` 라인과 이번에 구현할 `IMPL-API-NNN` task를 확인한다.
- 승인 문서에 이관 범위, 허용 수정 범위, 교체·삭제 허용, task, 테스트 범위가 있어야 한다.
- `Open`은 구현 전에 사람 결정이 필요한 질문에만 쓰므로 하나라도 있으면 blocker다. `Resolved`, `Pending Manual Evidence`, `Deferred`, production/cutover 전용 질문은 구현을 막지 않는다.

## 1. 착수 블록 — 코드를 만지기 전에 이 블록을 채워 출력한다

```
[구현 착수]
- 이번 묶음: IMPL-API-001, IMPL-API-002 (Full) / 승인된 스펙 전체 (Light)
- 이관 범위: <승인된 화면·API·동작·데이터>
- 허용 수정 범위: <파일·패키지·공유 컴포넌트와 교체·삭제 허용>
- 테스트 범위: <필수 단위·통합·계약 테스트와 verify 명령>
- binding 컨벤션: <Approved binding-rules 핵심 요약, 미등록이면 "미등록">
- 완료 조건: <승인 task 전체 + AC 전체 + verify PASS + 독립 검토 PASS>
- 이 Goal의 끝: READY FOR HUMAN REVIEW 또는 실제 [멈춤 보고]
```

**착수 블록이 이 턴의 계약이다.** 블록에 없는 파일을 만져야 하는 상황이 오면 그게 멈춤 조건이다.

## 1.1 실행 지속 게이트

- 승인 체크는 승인 범위의 구현·검증·수정 루프를 완료까지 실행하라는 사람의 명시적 요청이다. Goal 기능이 있으면 구현 파일을 만지기 전에 승인 task 전체를 `READY FOR HUMAN REVIEW`로 만드는 Goal을 생성한다. 이미 같은 Goal이 있으면 새로 만들지 말고 이어간다.
- 착수 블록을 출력한 직후 **같은 턴에서 첫 구현 도구를 호출한다.** `진행하겠습니다`, `다음 작업을 하겠습니다`, `이어서 처리하겠습니다`처럼 의도만 말하고 응답을 끝내는 것은 금지한다.
- 진행 상황은 commentary/update로 짧게 알릴 수 있지만 **final 응답으로 보내지 않는다.** 다음 안전한 작업이 남아 있으면 즉시 다음 도구를 호출한다.
- `그래`, `해`, `완성해`, `계속`, `끝까지`는 진행 중 Goal을 재분석하거나 재승인하라는 뜻이 아니라 이어서 실행하라는 뜻이다.
- 이미 승인된 다음 단계에 대해 `그래`, `해`, `계속할까요?` 같은 재확인을 요구하지 않는다.
- **턴을 끝낼 수 있는 경우는 단 두 가지다.** PASS 리포트를 포함한 `[완료 보고]`, 또는 파일·라인 근거를 포함한 `[멈춤 보고]`. 부분 패치, 코드 탐색, 컴파일 성공, 테스트 일부 작성은 종료 조건이 아니다.

## 2. 구현 — 세로 슬라이스

- task 하나(= API 하나)를 domain → repository → controller → 테스트까지 **한 번에 완성**한다.
- 착수 블록의 모든 task를 **중간 보고 없이 연속으로** 처리한다.
- 완성 후 정리 pass를 한 번 돈다: 책임 분리 · 이름(비즈니스 의도 — `data`/`result`/`temp`/`util`류 대신 도메인 언어) · 조건문(보호 절·빠른 반환) · null 흐름(실패의 원인 로그 보존, 명시적 실패 타입) · 추상화(필요가 확인된 것만).
- 주석은 이유·제약을 설명할 때만 쓴다. 리팩터링은 착수 블록 범위까지만 한다.
- **파일 생성·수정은 편집/패치 도구로 한다.** 셸 리다이렉트(`echo >`, `cat > … <<EOF`)로 코드 파일을 만들지 않는다 — 개행과 들여쓰기가 깨진다. 승인 게이트에 막히면 우회하지 말고 [멈춤 보고]로 알린다.
- 승인된 허용 수정 범위에 명시된 기존 코드 교체·삭제·공유 코드 수정은 정상 구현이다. 범위에 없는 새 독립 기능을 발견하면 구현 중 분석만 반복하지 말고 범위 밖 blocker로 보고한다.

## 3. 구현·검증·수정 루프

- 승인 task마다 다음을 연속 수행한다: ① 세로 슬라이스 구현 ② 해당 task 대상 테스트 ③ 실패 원인 수정 ④ 대상 테스트 재실행. 대상 테스트가 PASS하면 다음 task로 간다.
- 승인 task 전체가 끝나면 `./scripts/verify.sh`를 실행한다. FAIL이면 승인 범위 안에서 원인을 수정하고 다시 실행한다. 기존 실패는 승인된 baseline 예외와 정확히 일치할 때만 제외한다.
- 같은 실패 원인에 3회 연속 수정해도 결과가 같고 진전이 없을 때만 [멈춤 보고]한다. 서로 다른 실패를 순차 해결하는 것은 3회 제한에 포함하지 않는다.
- 다음은 즉시 [멈춤 보고]한다: 승인된 수정 범위 밖 파일 필요 / 스펙 변경 필요 / credential·unsafe 환경 / 테스트를 약화해야만 통과.
  - 테스트나 assertion을 느슨하게 만들어 통과시키지 않는다. 그건 수정이 아니라 은폐다.
- **PASS 없이는 [완료 보고]를 쓰지 않는다.**
- 성공 경로 + 빈 결과 + 잘못된 입력 + 외부 실패를 검증한다.
- Light: `03_Result.md`에 기록. Full: `04_Implement.md`(2-Pass·binding 대조)와 `05_Validate.md`(AC 단위)에 기록하고 tasks.md를 체크한다.
- 결과 상태는 `READY FOR HUMAN REVIEW`로 기록한다. 자동 검증 PASS만으로 완료 처리하지 않는다.
- verify PASS 뒤 `references/review.md`를 같은 Goal에서 실행한다. `FIX REQUIRED`가 승인 범위 안이면 발견을 고치고 대상 테스트 → verify → 독립 검토를 다시 수행한다. 사람에게 중간 승인을 요구하지 않는다.
- commit은 사용자가 명시적으로 요청했을 때만 한다. push/MR도 사용자 지시가 있을 때만 한다.

## 4. 완료 판정과 턴 종료

다음이 모두 참이어야 [완료 보고]한다.

- 승인된 IMPL task 전체 완료
- 연결된 AC 전체에 실제 test/evidence 존재
- formatter/lint가 구성된 프로젝트는 check PASS
- 최신 전체 verify report가 PASS
- 독립 검토가 `READY FOR HUMAN REVIEW`

하나라도 거짓이면 다음 안전한 도구 호출을 이어가며 final 응답을 보내지 않는다.

```
[완료 보고]
- 변경 사항: <파일별 요약>
- 설계 판단: <책임 배치와 구조를 이렇게 정한 이유>
- 검증 결과: <실행한 테스트와 결과>
- 검증 리포트: `reports/verify-<타임스탬프>.txt` (PASS)
- binding 대조: <규칙별 지켰음/예외(사유)>
- 남은 위험: <확인 못 한 것>
- 상태: READY FOR HUMAN REVIEW — `references/review.md` 독립 검토와 사람 최종 승인 필요
```

```
[멈춤 보고]
- 멈춤 조건: <범위 밖 변경 / 스펙·정책 변경 / credential·unsafe 환경 / 테스트 약화 없이는 통과 불가 / 같은 실패 3회 무진전 중 해당 항목>
- 발견: <파일:라인 인용>
- 질문: <사람이 결정할 것>
```

## 예시

❌ **이렇게 하지 않는다** (계층 쪼개기, 선언으로 종료, 형식 없음):

> core domain 4개 클래스를 추가했습니다. 다음으로 repository를 전환하고 목록 API부터 연결하겠습니다.

✅ **이렇게 한다**:

> [구현 착수]
> - 이번 묶음: IMPL-API-001~003 …
>
> *(3개 API를 domain→repo→controller→테스트까지 구현, 중간 보고 없음)*
>
> [완료 보고]
> - 변경 사항: VisitReviewController 외 9개 파일 …
> - 검증 결과: 테스트 14개 통과(빈 결과·잘못된 입력 포함) …
